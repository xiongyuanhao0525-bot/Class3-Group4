## 一、功能点 1：全站缓存策略优化（视图级缓存 + 自动刷新）

**改造前的问题**

`settings.CACHES` 已经配好缓存，`utils.py` 里也写了 `expire_view_cache` / `delete_sidebar_cache` 等失效函数，但真正能让「整页 HTML」被缓存的两条中间件（`UpdateCacheMiddleware` / `FetchFromCacheMiddleware`）在 `MIDDLEWARE` 里是**注释掉**的状态——缓存设施建好了却完全没用上。原有失效逻辑还是「手写枚举要删哪些 key」（如 `cache.delete('index_1')`），分页第 2 页以后、分类改名后的旧列表页都清不到。

**做法**

1. 新增 `djangoblog/cache_utils.py`：`versioned_page_cache` 装饰器给类视图加整页缓存（支持 CBV 的 TemplateResponse），响应头输出 `X-Cache: HIT/MISS` 便于验证；
2. 新增 `djangoblog/cache_signals.py`：监听 Article / Comment / Category / Tag / BlogSettings / Links / SideBar 的增改删（含 Article 标签 M2M 变更），把**全局版本号 +1**，所有历史页面缓存瞬间失效——比逐个 delete key 更可靠，不会漏；
3. 只缓存**匿名用户的 GET/HEAD** 响应，登录用户一律绕过，避免个性化内容串号泄露；
4. 「只更新浏览量」的保存（`update_fields={'views'}`）不触发整站刷新，避免热门文章把缓存刷穿；
5. 在 `blog/views.py` 给首页/分类/标签/作者/归档 5 个列表视图挂载缓存装饰器。

**效果**

`curl -I` 连续两次访问首页：第一次 `X-Cache: MISS`，第二次 `X-Cache: HIT`；修改任意文章后再访问自动变回 `MISS`。

**涉及文件**

| 文件 | 说明 |
|---|---|
| `djangoblog/cache_utils.py`（新增 142 行） | 版本号机制 + 视图级缓存装饰器 |
| `djangoblog/cache_signals.py`（新增 86 行） | 内容变更自动刷新信号 |
| `djangoblog/apps.py`（+6） | `ready()` 中注册信号 |
| `djangoblog/settings.py`（+8） | `PAGE_CACHE_ENABLED` / `PAGE_CACHE_TIMEOUT` |
| `blog/views.py`（+18） | 5 个列表视图挂载缓存；修复 `get_view_cache_key` 历史缺陷 |

## 二、功能点 2：安全加固（安全配置/响应头 + 敏感接口访问限流）

**改造前的问题**

原项目安全项只有 CSRF、`X-Frame-Options`、密码强度校验器、XSS 白名单，都属于**被动防御**。登录、注册、找回密码验证码这些「可以被脚本反复刷」的入口没有任何频率限制：能无限次撞库、批量刷注册、把找回密码邮件额度刷爆。这类滥用是 CSRF 拦不住的。

**做法**

1. `settings.py` 增加一组安全配置：
   - 无条件生效：`SECURE_CONTENT_TYPE_NOSNIFF`、`SECURE_REFERRER_POLICY`、`SECURE_CROSS_ORIGIN_OPENER_POLICY`、`SESSION_COOKIE_HTTPONLY`、同站 SameSite；
   - HTTPS 专属（默认随 `DEBUG` 自动开关）：`SECURE_SSL_REDIRECT`、`SESSION/CSRF_COOKIE_SECURE`、HSTS 一年、`SECURE_PROXY_SSL_HEADER`；
   - 特别地 `CSRF_COOKIE_HTTPONLY` 保持 **False**：前端 `commentSystem.js` / `reactionPicker.js` 需要从 cookie 取 `csrftoken` 放进请求头，设成 True 会让评论、表情接口全部 403（这是有意保留，不是漏配）。
2. 新增 `djangoblog/rate_limit.py`：`RateLimitMiddleware` 按「客户端 IP + 接口」做固定窗口计数限流，超限返回 **429** 并带 `Retry-After`、`X-RateLimit-Limit/Remaining/Reset`；只对登记的敏感接口生效（不搞全站限流，避免误伤正常浏览）；i18n 语言前缀归一化（`/en/login/` 与 `/login/` 共用计数）；默认不信任可伪造的 `X-Forwarded-For`。

**限流规则**

| 接口 | 上限 |
|---|---|
| `login/` | 10 次 / 60 秒 |
| `register/` | 5 次 / 300 秒 |
| `forget_password/` | 5 次 / 300 秒 |
| `forget_password_code/` | 3 次 / 300 秒 |
| `search/` | 30 次 / 60 秒 |

**涉及文件**

| 文件 | 说明 |
|---|---|
| `djangoblog/rate_limit.py`（新增 137 行） | 限流中间件 + 路径归一化 + 客户端识别 |
| `djangoblog/settings.py`（+39） | 安全配置组 + 限流规则 + 中间件注册 |

## 三、功能点 3：列表查询性能优化（消除 N+1）

**改造前的问题**

1. 列表页文章卡片模板 `article_info.html` 里有 `{{ article.comment_set.count }}`，会对**每篇文章**单独发一条 `SELECT COUNT(*)`——一页 10 篇就是 10 条额外 SQL（典型 N+1）；
2. 文章详情页沿用 `DetailView` 默认的 `Article.objects.all()`，模板访问 `article.category`、`article.author`、`article.tags.all` 时各触发一次查询，标签 N 个就再多 N 条。

**做法**

1. `djangoblog/mixins.py` 的 `OptimizedArticleQueryMixin` 增加 `Prefetch('comment_set', queryset=Comment.objects.only('id','article_id'))`：列表页评论计数改为内存 `len()`，SQL 条数从 `1+2N` 降到 `1+2`；
2. `blog/views.py` 的 `ArticleDetailView` 新增 `get_queryset()`：`select_related('author','category') + prefetch_related('tags', Prefetch('comment_set', ...))`，详情页关联查询总数固定，不随标签/评论数量增长；
3. 顺带修复 `ArticleListView.get_view_cache_key()` 的历史缺陷：原实现 `self.request.get['pages']` 对 HttpRequest 做下标访问，必然抛 `AttributeError`（当时该方法未被调用所以没暴露）。

**效果**

详情页取一篇文章并访问其标签/分类/作者/评论数，SQL 条数稳定为 3 条（主查询 + tags + comments）；无论标签是 1 个还是 6 个都不增长。

**涉及文件**

| 文件 | 说明 |
|---|---|
| `djangoblog/mixins.py`（+21 / -4） | 预加载评论计数（Prefetch 只取两列） |
| `blog/views.py`（+19） | 详情页 queryset 预加载 |

## 五、演示方式（视频录制时用）

两个新功能**默认在开发环境（DEBUG=True）关闭**，保证组员本地运行行为与改动前一致；演示时用环境变量开启：

```powershell
# 演示页面缓存（功能点 1）
$env:DJANGO_PAGE_CACHE='True'
python manage.py runserver

# 演示限流（功能点 2）：另开一次 runserver 时设置
$env:DJANGO_RATE_LIMIT='True'

# 演示安全响应头（功能点 2）：生产模式
$env:DJANGO_DEBUG='False'
python manage.py runserver
```
