## 2. 失败用例明细与根因

### 2.1 accounts — test_validate_register（1 ERROR）

- 位置：`accounts/tests.py:59`，`AccountTest.test_validate_register`
- 现象：`AttributeError: 'AccountTest' object has no attribute 'assertEquals'. Did you mean: 'assertEqual'?`
- 根因：测试方法调用了 pytest 风格的旧别名 `assertEquals`，Django `TestCase` 上不存在该方法，应为 `assertEqual`。属测试代码既有问题，与本轮功能改动无关。
- 归属：accounts（翟旌超）。
- 建议：将 `self.assertEquals(...)` 改为 `self.assertEqual(...)`。

### 2.2 comments — test_comment_rate_limit（1 ERROR）

- 位置：`comments.test_views.CommentSpamTest.test_comment_rate_limit`
- 现象：`django.db.utils.OperationalError: database table is locked`
- 根因：`comments/utils.py:23 send_comment_email` 在后台线程中发送评论邮件；邮件信号处理器 `djangoblog/blog_signals.py:51` 会写 `EmailSendLog` 并查询用户表。该后台线程写 SQLite 测试库时，与主线程事务竞争同一数据库连接/文件锁，导致表锁。线程内异常被 `Exception ignored in thread` 吞掉，表现为该用例 ERROR。
- 归属：comments 模块邮件发送链路 / 既有架构问题，非本轮 servermanager、plugins 改动引入。
- 建议：测试环境对邮件发送做 mock 或在测试中禁用后台线程；或将邮件落库记录与发信解耦，避免后台线程直接写测试库。

## 3. 全量测试阻塞说明

- 命令：`python manage.py test`（不带 app 标签）。
- 现象：运行过程中多次出现 `database table is locked`（日志中累计 44 次），进程未能输出最终 `Ran … / OK|FAILED` 汇总行。
- 根因：与 2.2 相同——评论邮件在后台线程写 SQLite 测试库，与主线程事务竞争锁；全量跑时用例集中、竞争更明显，导致整体无法跑通。
- 结论：该问题为既有架构在 SQLite 测试库下的并发限制，不属于本轮新增功能缺陷；在 MySQL 等支持并发写的数据库上通常不复现。分 app 单独运行时，除上述 2 个既有 ERROR 外其余用例均通过。
